# FAIX Chatbot System Architecture Report

## 1. Executive Summary
The FAIX Chatbot is a specialized AI assistant designed for the Faculty of Artificial Intelligence and Cyber Security. It utilizes a **Retrieval-Augmented Generation (RAG)** architecture to provide accurate, context-aware responses regarding course information, staff details, and schedules. The system runs locally using **Ollama** for privacy and cost-efficiency, integrated with a **Django** backend and a **React** frontend.

## 2. System Architecture Overview
The system follows a **Layered Micro-Service Architecture** pattern, divided into four primary layers:
1.  **Presentation Layer** (Client-Side)
2.  **Application Layer** (API & Business Logic)
3.  **Intelligence Layer** (AI & NLP Services)
4.  **Data Layer** (Persistence & Knowledge Base)

### 2.1 High-Level Data Flow
1.  **User Query**: The user inputs a message via the React interface.
2.  **Processing**: The Django backend receives the request, sanitizes input, and determines intent using Spacy.
3.  **Routing**: The `AgentRouter` directs the query to the appropriate specialized agent (FAQ, Staff, or Schedule).
4.  **Retrieval (RAG)**: Relevant context is fetched from the local Knowledge Base using semantic search (Sentence-Transformers).
5.  **Generation**: A context-enriched prompt is sent to the local LLM (Llama 3.2 via Ollama) to generate a natural language response.
6.  **Response**: The answer is returned to the user, and the interaction is logged for analytics.

## 3. Component Details

### 3.1 Presentation Layer (Frontend)
*   **Framework**: React (embedded in Django templates)
*   **Key Components**:
    *   `Chatbot.js`: Core widget logic, state management, and API communication.
    *   `Chat Interface`: Handles message rendering, typing indicators, and markdown formatting.
    *   **Demo Mode**: Specialized UI overlay for presentation purposes (metrics, quick actions).

### 3.2 Application Layer (Backend)
*   **Framework**: Django + Django REST Framework (DRF)
*   **Modules**:
    *   **API Views**: Endpoints for chat (`/api/chat/`) and feedback (`/api/feedback/`).
    *   **Guardrails**: Middleware to filter malicious inputs, gibberish, or out-of-scope queries before processing.
    *   **Session Manager**: Handles conversation history and context windows.

### 3.3 Intelligence Layer (AI Core)
This is the heart of the system, responsible for understanding and generating logic.
*   **Intent Detection**: Uses **Spacy** NLP to classify user intent (e.g., `find_staff`, `check_schedule`).
*   **Agent System**:
    *   `StaffAgent`: Specialized in faculty directory queries. Validates names against a "Safe List" to prevent hallucinations.
    *   `ScheduleAgent`: Handles timetable lookups and room locations.
    *   `FAQAgent`: General purpose queries using semantic similarity.
*   **Vector Search**: Uses `sentence-transformers/all-MiniLM-L6-v2` to generate embeddings for fast semantic retrieval.
*   **LLM Integration**: A custom `OllamaClient` wrapper communicates with the local **Ollama** instance running Llama 3.2.

### 3.4 Data Layer
*   **Operational DB**: **SQLite** (default) for storing active sessions, conversation logs, and user feedback.
*   **Knowledge Base**: Static **JSON/CSV** files located in `data/`. These serve as the ground truth for the RAG system, ensuring answers are based on faculty facts, not model training data.
*   **Analytics**: **Firebase** (optional) integration for long-term storage and dashboarding of chat metrics.

## 4. Key Technical Features

### 4.1 Local RAG Pipeline
Unlike cloud-based solutions, FAIX runs entirely locally.
*   **Privacy**: No data leaves the server; ideal for sensitive faculty data.
*   **Latency**: Optimized for low-latency retrieval (<200ms) and generation (<3s).

### 4.2 Hallucination Control
*   **Strict Context**: The LLM is prompted to *only* use provided context.
*   **Entity Verification**: Staff names generated by the LLM are cross-referenced against the internal directory before being shown to the user.

### 4.3 Scalability
The modular design allows for swapping the underlying LLM (e.g., to GPT-4 or Mistral) by simply updating the `OllamaClient` configuration, without changing the application logic.

---

## 5. Security & Performance
*   **Rate Limiting**: API endpoints are protected against flood attacks.
*   **Input Sanitization**: All user inputs are stripped of script tags and SQL injection patterns.
*   **Caching**: Common queries (greetings, simple FAQs) are cached to bypass the heavy LLM inference step.
